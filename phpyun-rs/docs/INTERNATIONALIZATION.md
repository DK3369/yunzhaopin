# 多语言规范

本文档规定 phpyun-rs 的多语言存储、读取、回退、缓存和接口行为。所有新增语言和新增可翻译内容都应遵循本规范。

## 一、基本原则

1. 接口返回给客户端的 `msg` 必须是最终显示文本，不能返回翻译 key。
2. 固定文案使用本地 JSON 文件；后台可修改的内容使用数据库。
3. 请求处理期间不得因为读取字典而查询数据库。
4. 动态字典必须启动加载到内存，修改后通过刷新机制同步。
5. 业务代码不能直接判断 `en`、`zh` 等语言来拼接文案，应通过统一的 i18n 或字典服务获取。
6. 翻译 key 必须稳定，不能使用中文原文作为 key。

## 二、语言来源和优先级

语言按以下顺序确定：

1. URL 参数：`?lang=en-US`
2. `Accept-Language` 请求头
3. Cookie：`lang=en-US`
4. 服务默认语言

当前支持的标准代码：

| 语言 | 标准代码 |
| --- | --- |
| 简体中文 | `zh-CN` |
| 繁体中文 | `zh-TW` |
| 英语 | `en` |

`en-US`、`en-GB` 等区域代码统一归一化为 `en`。新增语言时必须同时增加标准代码和常见区域代码映射。

## 三、固定文案

固定文案放在根目录 `locales/`：

```text
locales/
├── en.json
├── zh-CN.json
└── zh-TW.json
```

适合放入 JSON 的内容：

- 错误提示
- 页面和按钮文案
- 学历、经验、薪资、工作类型等固定枚举
- 不允许后台修改的固定分类
- 固定接口状态描述

推荐使用分组 key：

```json
{
  "errors": {
    "unauth": "Not logged in"
  },
  "dict": {
    "education": {
      "1": "High School"
    }
  }
}
```

JSON 会在编译时嵌入程序，运行时直接从内存读取，不产生文件 IO 和数据库请求。

## 四、动态字典和分类

以下内容允许管理员修改，不应只维护在 JSON 中：

- 职位分类
- 行业分类
- 地区分类
- 问答分类
- 后台可新增、删除、排序的字典
- 运营人员维护的多语言名称

数据库表是唯一数据源：

```text
phpyun_dict_i18n
├── kind       字典类型
├── item_id    字典项 ID
├── lang       语言代码
└── text       翻译文本
```

原始表中的 `name` 作为默认语言文本；`phpyun_dict_i18n` 保存其他语言或对默认语言的覆盖。

不要把同一批可编辑分类同时复制到 JSON 和数据库，否则后台修改后容易出现两套数据不一致。

## 五、缓存规则

动态字典统一使用 `dict_service`：

```text
服务启动
    ↓
一次性读取数据库
    ↓
构建 Dicts
    ↓
ArcSwap 保存内存快照
    ↓
接口只读内存
```

当前缓存规则：

- 启动时加载所有动态字典和翻译。
- 请求路径只做内存查找，不查数据库。
- 使用不可变 `Arc` 快照，刷新时整体替换。
- 后台定时刷新作为兜底机制。
- 管理员修改后调用 reload，并通过 Redis Pub/Sub 通知其他实例。
- 某个实例刷新失败时继续使用旧快照，不能影响正常接口返回。

刷新流程：

```text
管理员修改数据库
    ↓
当前实例重新加载并替换快照
    ↓
发布 dict_i18n:reload
    ↓
其他实例重新加载
```

## 六、翻译回退规则

动态字典按照以下顺序查找：

```text
当前语言
    ↓
简体中文
    ↓
英语
    ↓
原始表 name
    ↓
空文本
```

简体中文是历史数据默认语言。英语是系统级兜底语言。新增语言时，应明确它的回退链，不允许因为缺少翻译直接返回翻译 key。

固定 JSON 文案缺少翻译时，由 `rust-i18n` 按默认语言回退；最终不得把类似 `errors.unauth` 这样的 key 返回给客户端。

## 七、接口响应规则

成功响应统一为：

```json
{
  "code": 200,
  "msg": "ok",
  "data": []
}
```

错误响应统一为：

```json
{
  "code": 401,
  "msg": "Not logged in",
  "data": ""
}
```

规则：

- `msg` 放最终语言文本，不放 key。
- `data` 始终存在。
- 没有数据时，`data` 返回空字符串 `""`，不能省略或返回 `null`。
- 分类对象的 `name` 必须按照当前请求语言返回。
- 接口实现不应自行读取 JSON 或数据库，应调用统一 i18n / dict service。

## 八、新增语言流程

新增语言时按以下顺序处理：

1. 确定标准语言代码，例如 `ja`、`ko`、`fr`。
2. 在语言解析处增加标准代码和区域代码别名。
3. 新增 `locales/<lang>.json`。
4. 补齐 `errors`、`dict` 和固定业务文案。
5. 为数据库动态字典增加对应 `lang` 翻译数据。
6. 配置该语言的回退链。
7. 测试 `Accept-Language`、URL 参数和 Cookie 三种方式。
8. 测试缺少翻译时的回退结果。
9. 测试缓存刷新和多实例同步。

新增语言不应修改每个业务 handler。handler 只应传递字典类型、ID 和当前请求上下文。

## 九、命名规范

- 语言代码使用 BCP 47 风格，统一使用短横线，例如 `zh-CN`，不要使用 `zh_cn`。
- key 使用英文小写和下划线，例如 `errors.session_expired`。
- 动态字典的 `kind` 使用稳定业务名称，例如 `job`、`industry`、`region`。
- 不使用中文文案作为 key。
- 不把数据库自增 ID 直接当作固定文案 key；动态内容使用 `kind + item_id + lang` 唯一定位。

## 十、禁止事项

- 禁止在 handler 中直接写 `if lang == ...` 返回完整文案。
- 禁止每次请求查询 `phpyun_dict_i18n`。
- 禁止把动态分类复制到多个 JSON 文件作为第二数据源。
- 禁止返回翻译 key、中文原文或 `null` 作为错误 `msg`。
- 禁止新增语言时只增加 JSON，却不增加语言解析和回退配置。

## 十一、验证清单

每次增加或修改多语言内容后至少验证：

```bash
cargo fmt --all
cargo check --workspace
cargo test -p phpyun-core
```

接口验证示例：

```bash
curl -H 'Accept-Language: en-US' \\
  -H 'Content-Type: application/json' \\
  -d '{"kind":"job"}' \\
  http://127.0.0.1:3000/v1/wap/categories
```

至少检查以下情况：

- 英语请求返回英文。
- 简体中文请求返回简体中文。
- 繁体中文请求优先返回繁体翻译。
- 缺少翻译时按回退链返回。
- 缓存刷新后无需重启服务即可看到新翻译。
- 数据库不可用时，已有内存快照仍能正常返回。
